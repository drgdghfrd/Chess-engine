# ChessZero v1.1.0 Runtime Resources

The first v1.1.0 increment makes the Android/OEX runtime resource model explicit:

- `Threads = N` means N concurrent Lazy-SMP search contexts.
- `Hash = H MB` is the total TT budget, not H MB per thread.
- Contexts use private TT slices to avoid shared-lock contention.
- Thread/Hash changes made while idle are applied before the next search.
- `ucinewgame`/Clear Hash clears all active TT slices.
- Battery Saver remains controlled by the host GUI; the engine follows the UCI time budget supplied by the GUI.

For a 7-thread / 256 MB configuration, the current balanced splitter allocates 64 MB to the coordinator and 32 MB to each of the six workers: 256 MB total.

For a 5-thread / 128 MB configuration, it allocates 32 MB, 32 MB, 32 MB, 16 MB, 16 MB: 128 MB total.


## v1.1.0 runtime reconfiguration hardening

- `Threads` and `Hash` may be changed while an active UCI search is running. The engine performs a stop-and-join transaction before applying the new worker/TT layout.
- The cancelled search's `bestmove` is suppressed for option-triggered reconfiguration, so a GUI does not mistake the intermediate move for the next configured search.
- `isready` also quiesces an active search without emitting an intermediate `bestmove`.
- EngineAPI `setThreads()` and `setHashMB()` use the same stop-and-wait semantics instead of returning `engine busy`.
- After reconfiguration, ChessZero emits `info string runtime_reconfigured ...` and `isready` reports the applied thread count, total Hash budget, allocated Hash and worker count.

Battery Saver remains a GUI-side policy: standard UCI/OEX has no portable Battery Saver option. ChessZero therefore honors the time controls (`go movetime`, clock budgets, etc.) that the GUI sends rather than inventing a separate battery state.


### Runtime change transaction

For UCI/OEX, changing `Threads` or `Hash` while a search is active now follows:

`setoption` → request stop → wait/join all search workers → apply complete resource layout → emit `runtime_reconfigured` → next `go`.

The interrupted search does not emit a stale `bestmove`. This avoids a GUI consuming the cancelled move as if it were the result of the newly configured search.
