# ChessZero v1.1.0 — Runtime Threads/Hash Audit

## Scope
This change is the first Phase-1 increment for Android/OEX runtime resource control. It focuses on Threads, Hash and low-contention Lazy-SMP memory layout. Search heuristics and NNUE strength are intentionally unchanged.

## Runtime model
- `Threads` is the number of active Lazy-SMP search contexts.
- `Hash` is the total transposition-table memory budget across those contexts; it is not multiplied by the thread count.
- Each search context owns a private TT slice, avoiding a shared TT mutex in the search hot path.
- TT slices are power-of-two capacities because the current bucket layout is power-of-two indexed. The budget splitter keeps slices balanced and uses the whole requested budget when practical.
- Very small Hash values can give some workers a zero-sized TT while preserving the requested thread count.
- Switching Threads or Hash while the engine is idle reconfigures the worker pool/TT layout before the next search. UCI and EngineAPI already serialize these configuration changes outside active search.

## Battery Saver
Chessis owns its Battery Saver policy. The engine cannot directly observe a GUI-local Battery Saver toggle through standard OEX/UCI. ChessZero therefore does not fake such a signal or override GUI limits. It obeys the `go` command and its supplied time budget. When a host limits analysis to (for example) 5 seconds, the search hard deadline remains enforced.

## Important limitation
The distributed private-TT layout is designed to reduce synchronization contention. It has not yet been proven stronger than a shared-TT design by a statistically meaningful engine match. That comparison belongs to the next benchmark step before adopting further TT changes.
